# Меры защиты данных

## 1. Тегирование данных

### 1.1 Почему это нужно
Без тегов невозможно автоматически применять политики шифрования, удаления и контроля доступа. Теги — это метаданные, которые говорят системе "как обращаться с этими данными".

### 1.2 Какие теги внедрить

| Тег                   | Значения                                           | Назначение            | Пример                  |
|-----------------------|----------------------------------------------------|-----------------------|-------------------------|
| `classification`      | `public`, `internal`, `confidential`, `restricted` | Уровень секретности   | медкарта = `restricted` |
| `pii_category`        | `none`, `pii`, `sensitive_pii`, `medical`          | Тип ПДн               | диагноз = `medical`     |
| `retention_days`      | число (30, 365, 1825, 0=бессрочно)                 | Срок хранения         | анализы = 365           |
| `encryption_required` | `true`/`false`                                     | Нужно ли шифрование   | всегда `true` для PII   |
| `purpose`             | `treatment`, `billing`, `analytics`, `marketing`   | Цель использования    | влияет на доступ        |
| `consent_id`          | UUID ссылки на согласие                            | Для права на забвение | связь с согласием       |
| `anonymized`          | `true`/`false`                                     | Уже обезличено?       | для Data Lake           |

### 1.3 Инструменты тегирования

| Инструмент                  | Назначение                                  | Где применяется      |
|-----------------------------|---------------------------------------------|----------------------|
| **Apache Atlas**            | Тегирование в Data Lake / Hadoop            | Аналитический слой   |
| **Open Policy Agent (OPA)** | Политики на основе тегов                    | API Gateway, сервисы |
| **PostgreSQL комментарии**  | `COMMENT ON COLUMN ... IS '{"pii":"true"}'` | Операционная БД      |
| **S3 Tags**                 | Теги объектов                               | Data Lake, бэкапы    |
| **Custom metadata**         | В JSON-метаданных                           | Файловые хранилища   |

### 1.4 Пример политики OPA на основе тегов

```rego
# Политика доступа к медкартам
package data_access

default allow = false

# Врач видит только своих пациентов
allow if {
    input.role == "doctor"
    input.resource.tag.classification == "restricted"
    input.resource.tag.purpose == "treatment"
    input.resource.patient_id == input.user.patient_id
}

# Бухгалтер НЕ видит медкарты
allow if {
    input.role == "accountant"
    input.resource.tag.classification != "restricted"
}

# Аналитик видит только обезличенные данные
allow if {
    input.role == "analyst"
    input.resource.tag.anonymized == true
}
```

## 2. Шифрование
### 2.1 Шифрование при хранении (At Rest)

| Данные               | 	Инструмент                                    | 	Обоснование                                                 |
|----------------------|------------------------------------------------|--------------------------------------------------------------|
| Файловый сервер      | 	BitLocker (Windows) / LUKS (Linux)            | 	Защита от физической кражи диска                            |
| PostgreSQL БД	       | TDE (Transparent Data Encryption) или pgcrypto | 	Шифрование на уровне БД без изменения приложений            |
| 1С                   | 	Миграция на клиент-сервер + шифрование БД     | 	Файловый режим не поддерживает шифрование на уровне записей |
| Data Lake (S3/MinIO) | 	Server-Side Encryption (AES-256)              | 	Стандарт для облачных хранилищ                              |
| Бэкапы               | 	AES-256 + отдельные ключи	                    | Защита архивов                                               |


### 2.2 Шифрование при передаче (In Transit)

| Канал                     | 	Протокол                | Обоснование                            |
|---------------------------|--------------------------|----------------------------------------|
| Пациент → Портал          | 	TLS 1.3                 | Защита PII при передаче через интернет |
| Портал → API Gateway	     | mTLS + JWT               | Взаимная аутентификация + шифрование   |
| API Gateway → Сервисы     | mTLS                     | Защита внутреннего трафика             |
| ККМ → Платёжный шлюз	     | TLS 1.3 (замена OLE/TCP) | Защита фискальных данных               |
| Лаборатория → API Gateway | 	TLS + API ключи         | Защита анализов                        |
| Филиалы → Центр           | 	VPN (IPSec/WireGuard)   | Защита трафика между офисами           |

### 2.3 Управление ключами

| Компонент                     | Решение                          |
|-------------------------------|----------------------------------|
| Хранение ключей               | HashiCorp Vault / AWS KMS        |
| Ротация ключей                | Ежеквартально (автоматически)    |
| Резервное копирование ключей	 | Оффлайн, в сейфе                 |
| Доступ к ключам               | Только DevOps + Security Officer |

## 3. Обезличивание данных
### 3.1 Методы обезличивания

| Метод           | Описание                                                                | Когда применять                                   | Пример             |
|-----------------|-------------------------------------------------------------------------|---------------------------------------------------|--------------------|
| Токенизация     | Замена PII на случайный токен (с возможностью обратного преобразования) | Production, когда нужна связь с оригиналом        | ФИО → tok_7a8s9d0f |
| Псевдонимизация | Замена на хэш (SHA-256 + соль)                                          | Аналитика, когда нужна уникальность без раскрытия | email → a3f5e8d... |
| Маскирование    | Частичное скрытие                                                       | UI, логи                                          | +7 XXX XX-XX-12    |
| Агрегация       | Группировка в интервалы                                                 | BI-отчёты                                         | возраст: 30-40 лет |
| k-anonymity     | Обеспечение что каждая запись неотличима от k-1 других                  | Медицинские исследования                          | k≥5                |
| l-diversity     | Разнообразие sensitive значений в группе                                | Доп. защита после k-anonymity                     |                    |

### 3.2 Процесс обезличивания

#### Шаг 0: Исходные данные (PII + Medical)  
#### Шаг 1: Обнаружение PII и медицинских данных
- Регекс: email, телефон, паспорт, СНИЛС
- NER: ФИО, диагнозы, названия анализов
- Словари: ICD-10, LOINC, SNOMED CT
#### Шаг 2: Классификация по чувствительности
- Медицинские данные → medical
- PII → pii_high / pii_low
- Финансовые → finance
#### Шаг 3: Выбор метода обезличивания
- Если нужна связь с оригиналом → токенизация
- Если только аналитика → псевдонимизация
- Если UI → маскирование
- Если отчёты → агрегация + k-anonymity
#### Шаг 4: Обезличенные данные (отправка в Data Lake / Analytics)              

### 3.3 Инструменты обезличивания

| Инструмент                  | Назначение                                              |
|-----------------------------|---------------------------------------------------------|
| Privacy Vault (токенизация) | Замена PII на токены, хранение маппинга в защищённой БД |
| Apache Spark + ARX          | k-anonymity, l-diversity для больших данных             |
| Presidio (Microsoft)        | Обнаружение PII в тексте                                |
| OpenMined / PySyft          | Дифференциальная приватность для ML                     |

## 4. Контроль доступа (RBAC/ABAC)
### 4.1 Роли и права (RBAC)

| Роль          | Доступ к PII     | Доступ к медкартам   | Доступ к платежам | Доступ к аналитике  |
|---------------|------------------|----------------------|-------------------|---------------------|
| Пациент       | Только свои      | Только свои          | Только свои       | ❌                   |
| Врач          | Свои + пациентов | Свои + пациентов     | ❌                 | ❌                   |
| Ресепшен      | Все (для записи) | ❌ (только ФИО, дата) | Только сумма      | ❌                   |
| Бухгалтер     | ❌                | ❌                    | Все (для учёта)   | Только агрегаты     |
| Склад         | ❌                | ❌                    | ❌                 | ❌                   |
| Аналитик      | ❌                | ❌                    | ❌                 | Только обезличенные |
| Администратор | Все (по аудиту)  | Все (по аудиту)      | Все (по аудиту)   | Все (по аудиту)     |

### 4.2 Атрибуты для ABAC

| Атрибут        | Значения                         | Пример политики                          |
|----------------|----------------------------------|------------------------------------------|
| patient_id     | UUID пациента                    | Врач видит только своих пациентов        |
| purpose        | treatment, billing, analytics    | Аналитик видит только purpose=analytics  |
| classification | restricted, confidential, public | Бухгалтер не видит restricted            |
| consent_status | granted, revoked, expired        | При revoked — запретить доступ           |
| time_of_day    | working_hours, off_hours         | Доступ к медкартам только в рабочие часы |

### 4.3 Инструменты контроля доступа

| Инструмент              | Назначение                   |
|-------------------------|------------------------------|
| Keycloak / Auth0        | Identity Provider (IAM)      |
| Open Policy Agent (OPA) | ABAC политики                |
| PostgreSQL RLS          | Row Level Security в БД      |
| Apache Ranger           | Контроль доступа в Data Lake |
| Kerberos + LDAP         | Аутентификация в 1С          |
